# EduPath — JSON Schema and Application Data Contract

## 1. Project Overview

EduPath is an educational exploration platform for Class 10 students. It helps students record their academic background, interests, strengths, budget, and preferences to explore possible educational pathways after Class 10.

The application includes:

- Landing page and informational sections
- User registration and sign-in
- Authentication-protected student journey
- Student onboarding and profile management
- Academic information and subject preferences
- Interests and self-reported strengths
- Budget and funding preferences
- Educational destination preferences
- Pathway and scenario APIs

### Core Authentication Rule

**Students must register or sign in before starting their EduPath journey.**

Unauthenticated users can explore the public landing page, How It Works, Features, and About sections. They cannot access onboarding, their student profile, or protected dashboard pages.

The frontend must enforce the expected navigation behaviour, and the backend must enforce authentication and authorization for protected API operations.

---

## 2. Application User States

| State | Description | Permitted behaviour |
|---|---|---|
| Guest | User has not signed in | View public pages and informational sections |
| Registering | Registration request is in progress | Display loading state and prevent duplicate submission |
| Signing in | Login request is in progress | Display loading state and prevent duplicate submission |
| Authenticated, profile incomplete | User is signed in but has not completed onboarding | Start or continue the student journey |
| Authenticated, profile complete | User is signed in and has a saved profile | View or update the existing profile |
| Session expired | Existing session is no longer valid | Clear invalid authentication state and request sign-in |

The frontend must not treat a successful button click or a browser-stored boolean as proof of authentication.

## 5. Authentication Account Contract

Authentication and student profile information must remain separate.

### 5.1 Registration Request

Proposed request body:

```json
{
  "preferred_name": "Aarav",
  "email": "student@example.com",
  "password": "example-password"
}
```

### 5.2 Sign In Request

```json
{
  "email": "student@example.com",
  "password": "example-password"
}
```

### 5.3 Example Account Response

```json
{
  "user": {
    "id": 42,
    "preferred_name": "Aarav",
    "email": "student@example.com"
  }
}
```

These are example contracts. Adapt them to the actual backend response format.

### Account Validation

- Validate all fields on the backend.
- Normalize email addresses consistently.
- Prevent duplicate accounts for the same email address.
- Never store plaintext passwords.
- Never return passwords or password hashes.
- Use an established password-hashing algorithm.
- Do not accept client-supplied account IDs or administrative privileges.
- Use HTTPS in production.
- Do not store passwords in browser storage.
- Use the existing secure session or token implementation.
- Do not simulate successful authentication with a frontend-only flag.

## 7. Landing Page and Authentication Rules

### Guest State

When the user is not authenticated:

- Show Sign In and Register in the navbar.
- Keep the Start My Journey button disabled.
- Show the message: "Sign in or create an account to begin your journey."
- Keep See How It Works active.
- Allow access to public Home, How It Works, Features, and About sections.
- Do not allow access to onboarding, protected profiles, or the protected dashboard.
- Redirect direct navigation to protected routes to Sign In.

### Authenticated State

When the user is authenticated:

- Enable Start My Journey.
- Hide the guest Sign In and Register actions.
- Display an account menu with My Profile and Sign Out.
- Fetch the user's existing profile before deciding where to navigate.
- If no profile exists, direct the user to onboarding.
- If a profile exists, let the user continue to that profile or dashboard.
- Do not create duplicate profiles when a user signs in again.

### Session Expiry

When the backend rejects an expired or invalid session:

1. Clear the invalid frontend authentication state.
2. Do not continue to display the user as authenticated.
3. Redirect protected navigation to Sign In.
4. Preserve any unsaved form data where practical and safe.

Existing project API operations include:

|---|---|---|

| GET | `/api/profiles?skip=0&limit=10` | Retrieve profiles, subject to authorization |

| PUT | `/api/profiles/{profile_id}` | Update a profile |
| DELETE | `/api/profiles/{profile_id}` | Delete a profile |
| POST | `/api/pathways` | Submit a pathway request |
| POST | `/api/scenarios` | Submit a scenario request |

Verify these operations against the running backend before relying on them.

### API Requirements

- Preserve existing endpoint names unless the backend is deliberately updated.
- Validate all request data using backend schemas.
- Restrict profile access to the owning account or an explicitly authorized administrator.
- Never rely on a profile ID alone for authorization.
- Use appropriate HTTP status codes.
- Return clear validation errors without leaking sensitive information.
- Do not expose all students' private profiles to unauthenticated users.

## 10. Frontend Environment Variables

The frontend uses `VITE_API_BASE` to identify the backend base URL.

### Local Development

```env
VITE_API_BASE=http://localhost:8000
```

### Production

```env
VITE_API_BASE=https://edupath-ai-backend-9van.onrender.com
```

Environment variables prefixed with `VITE_` are exposed to browser code.

Therefore:

- Store only non-secret configuration in frontend environment variables.
- Never put passwords, database credentials, or private API keys in a `VITE_` variable.
- Do not commit real `.env` or `.env.local` files.
- Commit only placeholder-based example files such as `.env.example`.
- Configure production variables through the hosting platform.

## 11. Profile Validation Rules

1. The current project scope is Class 10 students.
2. Marks must not be negative.
3. Marks must not exceed maximum marks when both are supplied.
4. Percentages must be between 0 and 100.
5. Missing marks must be stored as `null`, never zero.
6. A strength rating must be between 1 and 5 or `null`.
7. An unrated strength should use the `not_sure` status.
8. An unknown budget must use a `null` amount and the `not_sure` status.
9. Budget amounts must not be negative.
10. The current budget currency is INR.
11. Interest and priority arrays must not contain duplicate values.
12. The backend must validate all incoming profile data.
13. The student's own interest description must not be silently replaced with generated content.
14. Unknown information must remain unknown rather than being invented.
15. Profile updates must not overwrite fields accidentally when the user edits only one section.

Cross-field validation rules should be implemented in the backend because JSON Schema alone does not enforce every relationship between fields.
